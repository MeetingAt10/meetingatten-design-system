## Team

- `scout` (read-only): file:line maps, grep sweeps, summarizing long test/build output. Send it first for every milestone.
- `coder`: implements a self-contained brief and runs the light checks named in it.
- `docs`: updates markdown docs to match finished changes (in-milestone doc edits like M1's mention stripping, and the M9 fold-in).
- Optional: `caveman:cavecrew-reviewer` for non-trivial diffs; `codex:codex-rescue` when stuck after two failed attempts on the same problem.

Every brief must stand alone: repo path, the spec section it implements (quote the relevant bullets), exact files, constraints from this prompt, the verification command, and the return format (diff summary + command output). Subagents have none of your context.

Parallel coders only on disjoint files and only when none of them runs a heavy command. Do tiny lookups and one-line edits yourself.

## Machine limits (low-power CPU)

Heavy commands always go through `pcore` and run one at a time, never from two agents at once: `pcore npm test`, `pcore npm run build` once it includes `tsc`, `pcore npx tsc ...`, `pcore npm --prefix site run build`, `pcore npm --prefix site ci`, `pcore npm ci`. The plain-Node scripts (`npm run check` before M5) are light. Prefer that heavy verification runs in your own session, not inside subagents.

## Milestone loop

For each milestone, in spec order (M1 → M9; M0 is a gate, see below):

1. Mark it in progress in the progress file.
2. `scout`: map every file the milestone touches; return a file:line table.
3. Brief `coder`(s) from the spec section. Split big milestones into slices.
4. Verify: run the milestone's "Verify" bullets yourself and paste the output into the progress file. Read the diff yourself. Visual milestones need screenshots (see below).
5. `docs` for any doc changes the milestone owns.
6. Commit on the milestone branch. Record in the progress file: commit hash, evidence, any deviation from the spec and why.
7. Save only durable decisions or lessons to memory. Continue to the next milestone.

## Stop and ask the user when

- A gate in the Authority table is reached.
- The spec contradicts itself, the code, or a settled decision, or does not cover something you need. Do not guess past a real gap; write the question into the progress file with your recommended answer.
- A check fails three times on the same cause.
- A contrast pair fails and the only fix touches a locked value.

When you stop, leave the tree committed or cleanly stashed, update the progress file, and give the user one concise question with your recommendation.

## Done when

Every "Success criteria (v0.3.0)" item in the spec has evidence in the progress file, the delta is folded into the master docs and moved to `context/deltas/archive/`, all milestone branches are committed locally, and nothing is pushed or tagged without approval. Then send the final report: summary, branches and commits, files changed per milestone, verification commands with results, remaining risks, and the list of follow-up deltas.
